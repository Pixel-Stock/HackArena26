# IBM Cloud Guestbook assignment

This folder contains the source and Kubernetes manifests for the Guestbook v1/v2 exercise.

## 1. Configure IBM Cloud and the cluster

Set your actual IBM Cloud namespace. Do not leave the placeholder in the deployment manifest.

```sh
ibmcloud login
ibmcloud cr region-set us-south
ibmcloud cr namespace-list
ibmcloud cr namespace-add <sn-labs-namespace>
ibmcloud cr login
ibmcloud ks cluster config --cluster <cluster-name-or-id>
kubectl get nodes
```

## 2. Build and push v1

Run from this `guestbook/` directory:

```sh
docker build -t us.icr.io/<sn-labs-namespace>/guestbook:v1 -f Dockerfile .
docker push us.icr.io/<sn-labs-namespace>/guestbook:v1
ibmcloud cr images
```

Save the actual `ibmcloud cr images` output as `crimages`. The image listing should include the repository and `v1` tag.

## 3. Deploy v1 and configure autoscaling

Replace `<sn-labs-namespace>` in `deployment.yml` with your actual registry namespace first.

```sh
kubectl apply -f deployment.yml
kubectl get deployment guestbook
kubectl autoscale deployment guestbook --cpu-percent=50 --min=1 --max=10
kubectl get hpa guestbook
```

Save the HPA table as `hpa`. HPA minimum replicas must be at least 1 on standard Kubernetes clusters; a stable HPA configured with minReplicas 0 is not generally supported unless the cluster enables the HPAScaleToZero feature and meets its requirements.

To generate CPU load, use a load-testing tool from a separate terminal, for example `hey` with multiple concurrent requests against the Guestbook service. Keep load running, then capture:

```sh
kubectl get hpa guestbook --watch
kubectl get deployment guestbook
```

Save the output showing an increased replica count as `hpa2`. Autoscaling requires the cluster metrics API (typically metrics-server) to be working.

## 4. Update to v2

```sh
cp up-app/index.html app/index.html
docker build -t us.icr.io/<sn-labs-namespace>/guestbook:v2 -f Dockerfile .
docker push us.icr.io/<sn-labs-namespace>/guestbook:v2
```

Save the complete Docker push output, including the final digest line, as `upguestbook`. Save the v2 HTML source as `up-app`.

Update the image in `deployment.yml` to `us.icr.io/<sn-labs-namespace>/guestbook:v2` AND change the Guestbook container CPU request from `10m` to `50m` in the same edit. Apply both changes together so they create one new Deployment revision:

```sh
kubectl apply -f deployment.yml | tee deployment
kubectl rollout status deployment/guestbook
kubectl rollout history deployment/guestbook
kubectl rollout history deployment/guestbook --revision=2 | tee rev
```

If your revision number is not 2, use the revision number shown by `kubectl rollout history`. The revision details should show the v2 image and updated CPU request. The manifest retains one old ReplicaSet so the post-rollback ReplicaSet listing can show the current and previous versions.

## 5. Roll back and capture ReplicaSets

```sh
kubectl rollout undo deployment/guestbook
kubectl rollout status deployment/guestbook
kubectl get rs
```

Save the actual `kubectl get rs` output after rollback as `rs`. Two ReplicaSets should be visible when the deployment has had two retained revisions and both are still listed.

## Evidence files

Capture genuine terminal output for `crimages`, `hpa`, `hpa2`, `upguestbook`, `deployment`, `rev`, and `rs`. Do not substitute example output: image digests, replica counts, revision numbers, and timestamps are generated by your environment.
